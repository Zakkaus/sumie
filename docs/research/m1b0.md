# M1b-0: native macOS evidence

Keep the Metal smoke page as the default. The primary evidence comes from one owner machine: a MacBook Air (Apple M2, 8 cores) with its built-in 60 Hz Retina display, running macOS 27.0.1 (26A434) in a logged-in desktop session. It used Rust 1.100.0, winit 0.30.13, and wgpu, wgpu-core and wgpu-hal 30.0.2. The files under [`m1b0/`](m1b0/) are copies of those runs. The GitHub `macos-15` results are a separate record; see [Hosted runner](#hosted-runner).

## 1. Native Quit: go for the hook design, not yet integrated

In M1b-0, `scripts/macos-spike/quit.sh CASE` rebuilt a standalone fixture against crates.io winit 0.30.13. It took the archive from Cargo's cache, checked it against the checksum in the workspace `Cargo.lock`, then applied `ordinary-quit.patch`. Since M1b-1 U2, it builds the pinned winit fork instead, whose diff is [`third_party/winit/0001-quit.patch`](../../third_party/winit/0001-quit.patch), and `ordinary-quit.patch` is gone. That M1b-0 patch added `applicationShouldTerminate:` to winit's own delegate class rather than installing a replacement delegate. It also added two opt-in methods to `ActiveEventLoopExtMacOS`:

- `intercept_quit(proxy, request)` arms the hook. The first `terminate:` sends one user event and returns `NSTerminateCancel`. Later requests return `NSTerminateCancel` and log `veto`.
- `finish_quit()` runs after the reap and queues a block on the main GCD queue through dispatch2 `DispatchQueue::main().exec_async`. The block checks winit's `EventHandler::in_use()`. If a nested run loop serviced the block inside a handler, the block logs `handler busy` and leaves the grant for that handler's return. The re-issued `terminate:` is the only one answered with `NSTerminateNow`.

The patch added no `unsafe`. The fixture and `sumie-macos` keep `#![forbid(unsafe_code)]`, and the `sumie-macos` winit requirement is now `=0.30.13`, matching the lock. Each case holds a `/bin/cat` child until 300 ms after draining starts, reaps it with `try_wait`, then calls `finish_quit`. Logs: `m1b0/quit-*.log`; phases are checked by [`check.py`](../../scripts/macos-spike/quit/check.py).

| Case | How both Quit requests enter AppKit | Result on this Mac |
| --- | --- | --- |
| `menu` | `performActionForItemAtIndex` on winit's Quit item | exit 0: request → draining → veto → reaped → grant → exiting |
| `key` | Cmd+Q `NSEvent` posted to the application queue (menu key equivalent) | exit 0, same phases; the posted repeat is vetoed before the reap |
| `cg` | Cmd+Q `CGEvent` posted to the PID through the window server (existing post-event access only) | exit 0, same phases |
| `nested` | `menu`, then a nested `NSRunLoop` inside the reaping handler | exit 0; the block ran inside the handler, logged `handler busy`, and was granted after the handler returned |
| `synchronous` (control) | `menu`, but `finish_quit` re-issues `terminate:` synchronously | SIGABRT at `event_handler.rs:135` "tried to handle event while another event is currently being handled", from `app_will_terminate` |
| `nested-queued` (control) | `nested`, but the window is dropped first, which queues winit events | SIGABRT at the same check, from winit's own `queue_closure` |

`scripts/check-gate.py macos-quit` runs the three positive cases and `scripts/negative-controls.py macos-quit` runs the two controls. A control fails unless the panic location and its originating frame match; timeouts, build errors and other non-zero exits do not count.

**M1b-1:**
- Move the patch to a reviewed fork commit and pin it with `[patch.crates-io]`. Drop the `eprintln!` phase markers.
- Handle the system Quit reason (`NSTerminateLater` plus a reply that works in modal run-loop mode) before arming the hook. As written, the hook would veto logout.
- Never run a nested run loop or modal session inside a winit callback: the `nested-queued` control shows that winit 0.30.13 itself panics.

## 2. Metal surface ownership

`scripts/macos-spike/metal.sh` links [`metal.m`](../../scripts/macos-spike/metal.m) into a winit and wgpu 30.0.2 probe. The hook swizzles `-[CAMetalLayer nextDrawable]` and the concrete `MTLCommandBuffer -setLabel:`. It requires the acquiring window to be visible (including `NSWindowOcclusionStateVisible`) and records each acquire's IOSurface and wait. An external watchdog sends a numbered `PING` every 50 ms, and only the winit main-thread handler answers it. GPU holds wait on per-frame `MTLSharedEvent` values encoded into wgpu's own submissions. A GCD worker releases them one value at a time. Results are in `m1b0/metal.json`, with traces in `m1b0/metal-*.trace`.

| Scenario | Observation (M2, macOS 27.0.1) |
| --- | --- |
| `held`: three presents gated on unsignaled GPU events, then a fourth acquire | **No exhaustion.** With `maximumDrawableCount` = 3, the fourth `nextDrawable` returned a fourth IOSurface after 7.9 ms. Retaining unpresented drawables, the previous design, also allocated fresh surfaces. |
| `fifo`: 240 unthrottled presents on the visible window | **Real exhaustion by the compositor.** Acquires cycled through exactly 3 surfaces; after the first three, the wait had a median of 15.0 ms, p95 16.3 ms and maximum 16.6 ms, all on the main thread. The worst ping after BEGIN took 17.6 ms. |
| `occluded`: FIFO, then an opaque always-on-top window covers the probe | wgpu reported `Occluded` after 63 frames (62 when minimized); `frames_before_wgpu_occluded` in `metal.json` counts from the start of the case. The worst ping during the case was 42.3 ms. Six raced acquire-and-present cycles that bypassed wgpu's check, with Apple's drawable timeout temporarily enabled, each returned within 9 ms. |
| `minimized`: the same race, with the window minimized | The raced acquires again each returned within 9 ms. The minimize animation alone left winit proxy pings unanswered for **596 ms**. |
| `busy-resize`: real window resize while a submission waits on a GPU event | **Blocked.** `Surface::configure` held the main thread for 406 ms, until the watchdog released the GPU, and the layer reached the new size only after that release. |
| `deferred-resize`: the same resize, configuring only when `device.poll(Poll)` reports an empty queue | **Responsive.** The main thread kept answering pings, with a worst round trip of 0.17 ms during the 419 ms hold, then configured in 0.17 ms after the GPU finished. |

**Decision.**
- **Configure: go for the main-thread path.** The readiness condition is an empty submission queue; resize keeps the latest size and retries on the next wake.
- **Acquire: not proven, so the main-thread-only path does not pass M1b-0.** On a visible window, GPU completion does not decide when a drawable returns: the pool grows under GPU holds, and the compositor paces it. The wait stayed bounded by one refresh in every state tested, but wgpu-hal disables the drawable timeout. Display sleep, screen lock, Spaces switching and display disconnect were not tested because they would change the owner's session. An unconsumed pool in any of those states would block the main thread indefinitely.
- **The worker-acquire HAL patch was not prototyped** and keeps the plan's conditions.

**M1b-1:** Choose between two options:
- A pinned wgpu-hal change that enables `allowsNextDrawableTimeout`, giving at most about 1 s per stall, and keeps the visibility check on the main thread.
- Owner evidence for the four untested states.

Either way, redraw from one display-paced frame slot: presenting faster than the display costs about 15 ms of main-thread time per frame.

## 3. Capabilities and timing baseline

`scripts/macos-spike/baseline.py 5 DIR` runs `runner.sh` five times. Each run is a 60-second timing sample with an alternating clear color, followed by a capability inspection of the actual smoke window. The summary is in `m1b0/baseline.json`; per-run reports are in `m1b0/baseline-run-N-{timing,capabilities,environment}.json`. Neither preflight requested access or changed TCC. Screen capture and CGEvent posting were attempted only because the preflights reported existing access.

| Capability | This Mac (5/5 runs unless noted) | GitHub `macos-15` arm64 |
| --- | --- | --- |
| Window on WindowServer, Metal present | supported | supported ([CI run on 9fdfb1e](https://github.com/Zakkaus/sumie/actions/runs/45396164490/job/138452398930), workflow `CI`, Metal smoke, three frames) |
| Key window / content view first responder | supported | supported (3/3, [run 45619247016](#hosted-runner)) |
| `NSApp.postEvent` F13 down/up reaches winit's handler | supported | supported (3/3, [run 45619247016](#hosted-runner)) |
| Quit menu dispatch (`menu`, `key`, `cg` cases above) | supported | `menu` and `key` supported; `cg` not run ([run 45619247016](#hosted-runner)) |
| Named pasteboard round trip (general board untouched) | supported | supported (3/3, [run 45619247016](#hosted-runner)) |
| `CGPreflightScreenCaptureAccess` / `CGPreflightPostEventAccess` | true / true (inherited from the launching terminal) | true / true (3/3, [run 45619247016](#hosted-runner)) |
| Known-pixel window capture / targeted CGEvent F14 | supported / supported (diagnostic only) | supported / supported (3/3, [run 45619247016](#hosted-runner)) |

The five runs completed between 23:40 and 23:45 local time on 2026-11-25, with a 1-minute load average of 3.1–5.5 before each run. A system daemon (`identityservicesd`) was using about one core when the runs started. Submission is the renderer's presentation call, not display time.

| Metric | Median | Min–max | Samples (ms) |
| --- | --- | --- | --- |
| Launch to first present, as observed by the controller | 192.5 ms | 187.9–288.3 | 288.3, 188.4, 187.9, 196.9, 192.5 (first run cold) |
| Worst main-thread ping round trip over 60 s (1,201 pings at 50 ms) | 16.5 ms | 9.5–19.6 | 9.5, 16.5, 19.6, 15.7, 18.3 |
| Longest submission gap over 60 s, including the tail (about 3,600 submissions) | 17.8 ms | 17.7–25.8 | 25.8, 17.8, 17.7, 18.0, 17.8 |
| Native window close to reaped process exit | 132.5 ms | 131.6–133.6 | 132.4, 133.6, 132.5, 133.0, 131.6 |

All runs met the 100 ms response, 100 ms submission-gap and 6 s close targets on this Mac with margin. Native Quit was not part of the close timing; the five `menu` repeats ran from launch to exit in 0.53–0.64 s, including the fixture's 300 ms child hold (`m1b0/quit-summary.txt`). The `minimized` Metal case shows that these steady-state numbers do not cover AppKit animations.

## Hosted runner

[Run 45619247016](https://github.com/Zakkaus/sumie/actions/runs/45619247016) of `.github/workflows/macos-spike.yml` on `spike/m1b0` (commit `d9bfd31`) passed all five jobs, each on a fresh `macos-15` arm64 VM: macOS 15.8.2 (24H232), image `20261118.0550.1`, 3 logical CPUs, Rust 1.100.0. Every job started about a minute after boot, with a 1-minute load average of 48–117. The artifacts are copied under [`m1b0/hosted/`](m1b0/hosted/).

- **Capabilities (`runner-1` to `runner-3`):** all three samples support the window server, key window, first responder, named pasteboard, AppKit and targeted CG key delivery (down and up reached winit), and known-pixel capture. Both preflights were true.
- **Quit (`quit-1`):** `menu`, `key` and `nested` exited 0 with the same phases as on the owner's Mac; `nested` again logged `handler busy` before the grant. Both controls panicked at `event_handler.rs:135`: `synchronous` from `app_will_terminate`, `nested-queued` from winit's `queue_closure`. The `cg` case was not run.
- **Metal (`metal-1`, `hosted/metal.json`):**

| Scenario | Hosted observation |
| --- | --- |
| `held` | Not reproduced: a fourth IOSurface after 6.7 ms. |
| `fifo` | 3 surfaces; acquire median 15.0 ms, p95 17.2 ms, **max 108.5 ms**; worst ping 102.1 ms. |
| `occluded` | wgpu reported `Occluded` after 65 frames; six raced acquires each returned within 0.23 ms. Worst ping **1,025.8 ms**, unexplained. |
| `minimized` | Raced acquires each returned within 9.7 ms; worst ping **638.3 ms**. |
| `busy-resize` | Reproduced: configure blocked the main thread for 405.5 ms; worst ping 378.7 ms. |
| `deferred-resize` | Responsive: worst ping 1.7 ms during the 416.5 ms hold; configure took 0.54 ms. |

Timing from the three 60-second `runner` samples (`hosted/runner-N-timing.json`):

| Metric | `runner-1` | `runner-2` | `runner-3` |
| --- | --- | --- | --- |
| Launch to first present, as observed by the controller | 1,350.4 ms | 1,326.1 ms | 1,854.4 ms |
| Worst main-thread ping round trip | 66.1 ms | 46.4 ms | 95.1 ms |
| Longest submission gap | 68.6 ms | 65.4 ms | **134.8 ms** |

`runner-3` missed the 100 ms submission-gap target; every sample met the 100 ms ping and 6 s close targets. M1b-1 turns these capabilities into hard hosted gates, starting with the Quit cases and controls, which now run on every push as the `macos-quit` job in `ci.yml`. Hosted timing stays recorded only: the 100 ms response and submission and 6 s cleanup targets are judged on the owner's Mac.
