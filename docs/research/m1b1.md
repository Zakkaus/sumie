# M1b-1: native macOS evidence

Same owner machine as [M1b-0](m1b0.md): MacBook Air (Apple M2), built-in 60 Hz Retina panel, macOS 27.0.1 (26A434), Rust 1.100.0, the pinned winit fork. Copies of the runs are under [`m1b1/`](m1b1/).

## U4: wake source and AppKit animations

**Wake scenario (`check-gate.py macos-wake`).** From `run_after_handler`, the main thread runs the default, event-tracking and modal-panel modes for 300 ms each. Another thread writes a pipe watched by the readiness bridge 100 ms into each mode. In every run on this Mac, the write reached the handler in the same mode within 0.09–3.2 ms. With the control (a default-mode-only `performSelectorOnMainThread:` wake), the default mode still passed (4.3 ms), while event tracking and modal panel got no wake inside the interval.

**Pings during animations.** `scripts/macos-spike/animations.sh` starts the runner in its `idle` mode, which presents one frame and then answers only pings, steps and close. A ping goes over stdin to the same `EventLoopProxy` run-loop source the bridge uses, and the controller sends one every 10 ms. The table gives the worst round trip in each phase over three runs, `m1b1/u4/run-{3,4,5}.json`, taken at 02:58–03:00 on 2026-11-26 with a 1-minute load average of 2.7–4.7. `sampled.json` repeats the sequence with `sample` attached.

| Phase | Worst ping (3 runs) | Pings over 100 ms | Who stalls |
| --- | --- | --- | --- |
| Idle, 2 s | 0.4–1.1 ms | 0 | — |
| Cmd+M `CGEvent`, handler idle | 15.4–24.1 ms | 0 | Nothing minimized: winit's default menu has no Window ▸ Minimize item, so Cmd+M has no key equivalent. |
| Minimize button clicked with a `CGEvent`, handler idle | 552.8–585.4 ms | 38–41 | `AppKit` |
| `set_minimized(true)` through `run_after_handler` | 554.9–574.0 ms | 38–40 | `AppKit` |
| `set_minimized(true)` inside the handler (diagnostic) | 546.7–573.5 ms | 38–39 | `AppKit` |
| Restore through `run_after_handler` (after each minimize) | 519.0–548.4 ms | 34–38 | `AppKit` |

**The minimize stall (547–599 ms worst ping across runs) is AppKit's, not ours.** All three minimize triggers starve pings by about the same amount. That covers a click on the minimize button while the handler is idle, `run_after_handler`, and the in-handler call. In every one, `sample` shows the main thread inside `-[NSWMWindowCoordinator clientWindowManager:windowMiniaturizationResponse:]` → `-[NSWindow _regularMinimizeToDock]` → `minimizeItems`, which runs its own nested run loop (387–430 of about 1,400 samples). No sumie frame sits under it. That nested loop accounts for about 390–430 ms of each stall; the remaining ~150 ms is in the surrounding transaction wait (`waitForTransaction`), also with no sumie frame. The run-loop mode was not recorded, so "the proxy source is not serviced there" is inferred from the stacks, not observed. Restore stalls the same way in `windowDeminiaturizationResponse:`. Under plan rule 1.5 these are owner-reviewed exceptions with their stacks (`m1b1/u4/sample-minimize-*-main.txt`, `sample-restore-1-main.txt`), not passes.

**The live-resize stall is ours.** The smoke page redraws inside the Core Animation commit (`drawRect:` → `RedrawRequested` → `Smoke::draw_with`). There it blocks in `wgpu::Surface::get_current_texture` → `-[CAMetalLayer nextDrawable]` (295 of 640 samples in the semaphore wait; `sample-live-resize-main.txt`). U8's display-paced frame slot and empty-queue configure replace this path. The live-resize result counts against the 100 ms rule until U8 measures it again.

Not measured here: a Space switch (it would change the owner's session) and the hosted runner, where pings are recorded only.

## U8: terminal driver, frame slot and configure

`SUMIE_MACOS_DRIVER=terminal` runs the shared session in the `AppKit` window. All runs below used the debug build with `macos-ci`, on 2026-11-26 between 04:00 and 04:35 with a 1-minute load average of 2.0–4.8. The runner is `SUMIE_MACOS_CI_RUNNER=terminal`, with [`frame-hook.m`](../../scripts/macos/frame-hook.m) injected. Copies are under [`m1b1/u8/`](m1b1/u8/).

**Gates and controls (`check-gate.py macos-{resize,idle,flood,timeout}`).** Each control exited 1 with its marker. The ranges cover three to five passing runs of each gate's final version. Two earlier idle runs are not in the table: one saw a present 24 s in, before the gate logged focus changes, and in the other the runner exited within 3 s without a diagnostic. Neither recurred in four later starts or four idle runs.

| Gate | Result on this Mac | Control | Control result |
| --- | --- | --- | --- |
| `macos-resize`: a CG drag of the corner over 1.2 s while one wgpu submission waits 0.8 s on an `MTLSharedEvent` | 37–38 configures deferred to a later refresh, 39–41 configures after the release, **0 on a busy queue**; worst ping 3.0–7.5 ms | configure on `Resized` | 1 configure on a busy queue blocked the main thread; worst ping **670 ms** (M1b-0 `busy-resize`: 406 ms) |
| `macos-idle`: 60 s, cursor blink off, `/bin/sh` | **0 presents** | present every turn even when clean | 15 presents within 0.3 s |
| `macos-flood`: `seq 1 999999999`, presents and acquires from 0.5 s to 3.0 s | 150 presents in 2.48 s, **1.00 per 16.67 ms refresh**, gaps min 16.2 ms, median 16.66 ms; acquire median **0.01 ms**, max 0.02–0.05 ms; worst ping 1.2–1.6 ms | free the slot on every wake | acquire median **12.9 ms**, max 15.5 ms: the FIFO wait is back |
| `macos-timeout`: the next two `nextDrawable` calls return nil | nil, nil, then a drawable, **1.001–1.005 s** and **2.002–2.004 s** apart; worst ping 2.7–9.7 ms | the 50 ms retry | acquired again after 53 ms, twice |

`yes` cannot drive the flood check: its lines are identical, so the scrolled screen never changes and, correctly, nothing presents. The first version of the slot restarted from each present and drew every 18 ms (0.92 per refresh); the slot now keeps its cadence. A present after a late one can then come sooner: with six `yes > /dev/null` processes loading the CPU, single gaps fell to 7.4 ms, yet any two gaps spanned at least 24.1 ms and the rate stayed at 1.00 per refresh. The gate therefore checks the rate and the span of two gaps (at least 0.85 of a refresh, allowing for turn-end timestamps). A median gap of 16.66 ms shows no drift against the 60 Hz panel, so the plan's CADisplayLink fallback is not needed here. A 120 Hz ProMotion panel stays an owner check.

**Live, in the real login shell** (`/bin/zsh` with the owner's profile). The runner's `type` command entered the commands; keys are U9. `DISABLE_AUTO_UPDATE=true` in the runner's environment kept oh-my-zsh's update prompt from waiting for an answer, and no user file changed. Captures are in the review evidence (`u8-evidence/live/*.png`), not in the repository.

- **`yes | head -c 209715200`** (BSD `head` rejects `200M`) finished in 117.6 s. The worst of 8,591 pings took 4.0 ms. There were 8 presents, because the screen stops changing. A release build gives the same rate: 50 MiB of `yes` in 33.7 s and `seq 1 6000000` (66 MB) in 9.4 s, with pings at 0.1 ms, so the main thread is mostly idle. A bare Python reader of the same `yes` gets 5 bytes per read and 2.8 MB/s, and sumie's reader about 2.3 MB/s. The limit is the writer, not the reader (see PTY throughput below).
- **Two CG drags** (+240 × +138 pt, then −300 × −177 pt) followed by `stty size`. The child printed `15 47`. The VT snapshot was 15 rows × 47 columns. The first capture after the output shows `15 47` with the prompt wrapping at column 47. The worst ping during the drags was 6.3 ms. U4's 143 ms live-resize stall belonged to the smoke page; the terminal driver does not draw inside `drawRect:`.
- **Cover and restore.** An opaque floating window covered the window for 3 s while the shell printed. Occlusion arrived at +0.10 s and its end at +3.24 s. Nothing presented while the window was covered. One present at +3.25 s shows the output written meanwhile (`after-restore.png`).
- **Fullscreen in and out** through `run_after_handler`: worst ping 20.3 and 11.9 ms, 2 presents each.
- **CJK and box drawing** (`cjk-box.png`): box lines join across cells, and Japanese, Chinese and Korean use the Core Text fallback.

Not run: a switch to another Space. There is one desktop Space, and the second Space belongs to another application's fullscreen window. The fullscreen transition above is the window's own Space change. Cmd+M was not run either: U4 found no Minimize item in winit's menu.

## PTY throughput on macOS

U8 left open why `yes | head -c 209715200` reached only 1.6–2.3 MB/s, with about 5 bytes per read. All runs were on 2026-11-26 between 04:50 and 05:20. The 1-minute load average was 5–15, because another agent was building on the same Mac. Bench rows come from a temporary harness, not committed. It drives `sumie_pty::Pty` with a consumer that only counts, or a bare PTY reader with a 64 KiB buffer, and reports MB/s of PTY output (including the tty's CR). App rows type the command into the debug terminal runner and time it with marker-file mtimes.

**The writer makes the 5-byte reads.** BSD `head -c` copies byte by byte with stdio. On a tty, stdout is line-buffered, so it issues one 2-byte `write(2)` per `y` line. Every reader sees those writes one or two at a time:

| Workload | sumie `Pty`, fast consumer | bare blocking read, 64 KiB | bare Python `os.read` | app, debug / release |
| --- | --- | --- | --- | --- |
| `yes \| head -c` | 2.0–2.5 MB/s, 7 B/read | 1.9–2.7 MB/s, 5–7 B/read | 2.6–2.8 MB/s, 5 B/read | 2.1–2.8 / 2.15 MB/s |
| Python, 2-byte `os.write` loop | | 2.1 MB/s, 3 B/read | | |
| `yes \| head -c \| cat` | | 88 MB/s, 1017 B/read | | |
| Python, 64 KiB `os.write` loop | | 106 MB/s, 1020 B/read | | |
| `yes` alone, 1 s | | 62 MB/s, 989 B/read | 128 MB/s, 963 B/read | |
| `seq 1 3000000` | 8.1 MB/s, 22 B/read | 7.0 MB/s, 13 B/read | | |
| `head -c 64M /dev/zero \| base64` | 118–137 MB/s, 1024 B/read | 184 MB/s, 1024 B/read | 190–200 MB/s | 78–102 / 40–99 MB/s |

The suspects the task named are ruled out:
- **Read buffer size.** A master read never returns more than 1024 bytes, so neither the reader's 8 KiB buffer nor 64 KiB changes anything. Raising the tty speed (`t_hiwat` follows `t_ospeed`) from the default 9600 to 38400 or 230400 does not change the size or the rate either.
- **Eager non-blocking reads.** Pausing after each short read lets data pile up: 100–480 B per read at 20–200 µs. The rate moves only from 2.7 to 3.1 MB/s, and drops to 1.1 MB/s at 500 µs, once the queue stops the writer.
- **Reading until EAGAIN into 64 KiB before each send.** Prototyped and reverted: 9 B per chunk and 2.2 MB/s for `yes | head`, 1 KiB per chunk for base64. The reader always catches up with the writer.
- **Re-arm before drain and the consumer.** During 50 MiB of `yes | head` in the app, the reader spent 7% of its time blocked in `send`. The pane took about 14 chunks per drain at 22,000 drains/s, and the VT used 3.5 s of 33 s. For base64, the VT used 0.15 s of 3 s.

**No change to the reader.** No read-side change raises a line-at-a-time writer's rate, and Linux shares the code, so `sumie-pty` stays as it was. `ARCHITECTURE.md` now records the constraint. On Linux the same `yes | head` is fast because GNU `head` writes whole blocks.

**Check.** `check-gate.py macos-throughput` (`frames.py throughput`) types `head -c 67108864 /dev/zero | base64` into the terminal runner. It requires 89,478,488 bytes at 20 MB/s or more, and gives up after 4.5 s plus 0.5 s. On this Mac it measured 92.8–102.1 MB/s over eight runs at load 13–14 (debug; [`m1b1/pty/frames-throughput.json`](m1b1/pty/frames-throughput.json)). The first run after a fresh link was the slowest: 31.8 MB/s in debug and 39.8 MB/s in release. Control (`negative-controls.py`): an 8-byte read buffer. It exits 1 with `took over 4.5 s (below 20 MB/s)` after about 7 s; left to finish, it measures 2.5–3.7 MB/s. With `SUMIE_TIMING=record`, the rate is only reported and the control does not run.

## U10: close and Quit contract, deadlines, resource loop

Debug build with `macos-ci`, 2026-11-26 05:00–06:10 local, 1-minute load average 4–6 (another agent was building). Each case is a fresh terminal runner whose `/bin/sh` runs `trap '' HUP; sleep 1000` (`scripts/macos/lifetime.py`); times are from the trigger, or from the logged start of draining for the stuck cases.

| Case (3 runs each, runner triggers) | Result on this Mac |
| --- | --- |
| `close` (`performClose:`) | off screen by 0.37–0.45 s (sampled when the CGWindowList query returns), SIGKILL 3.10 s, reaped 3.10–3.11 s, exit 0 at 3.12 s. Off screen includes the 0.1 s a `CloseRequested` queued behind the runner's handler waits, and `AppKit`'s close animation; the real red button: SIGHUP at 0.02 s |
| `repeat` (two `terminate:`, 1.5 s apart) | intercept, veto, grant; SIGKILL 3.00 s after SIGHUP; exit 0 at 3.02 s |
| `fatal`, `fatal-quit` | exit 1 with `sumie: injected fault` at 3.01–3.02 s; SIGKILL 3.00 s after SIGHUP; no Quit phase, and `intercept` alone during a Quit (no grant) |
| `system`, `system-fatal` (self-sent `aevt/quit`, `why?` = `rlgo`) | later, then reply at 3.00–3.01 s (limit 4 s), exit 0; with the error, it is logged and the reply still goes out |
| `stuck`, `stuck-system` (runner `stall` while reaping) | exit 70 at 10.02–10.03 s, exit 0 at 6.02–6.03 s; the watchdog logs `stage="reaping" open=1`; no reap is reported |
| `exit` in the last shell | off screen 0.06 s, exit 0 |

**Controls** (each exits 1 with its marker): window kept until exit → off screen 3.13 s, after the reap at 3.10 s; no SIGKILL at the grace period → no SIGKILL, watchdog exit 70; `replyToApplicationShouldTerminate:NO` → the watchdog ended the process 6.01 s after the request; no watchdog → still running 10.5 s (6.5 s) after the quit.

**Live input** (`SUMIE_LIFETIME_TRIGGER`; Accessibility and Screen Recording were already granted, nothing was changed): the red button (a CG click on the AX close button) passed `close` (off screen 0.51 s, SIGKILL 3.0 s after SIGHUP). Cmd+Q through the HID tap (only after checking the runner is frontmost), an AX press on "Quit sumie" and the Dock item's Quit (AX `AXShowMenu`, then the item titled with the Dock's own `QUIT` string, here 結束) each passed `repeat`, `fatal-quit` and `stuck`. The Dock's Quit sends an ordinary quit event, so it is intercepted, vetoed on repeat and granted once.

**200 open/close cycles in one process** (runner `cycle`: `performClose:`, drain, a new driver and window): 30.5–33.0 s, about 150 ms per cycle. Five runs (one of 400 cycles) ended at the first window's counts, except one run with 14 threads instead of 13; the 400-cycle run ended at 13, so the extra thread was transient, not a leak.

| Measured 1.5 s after the window presents | First window | After 200 cycles |
| --- | --- | --- |
| Descriptors (`lsof -p`) | 55 | 55 |
| Threads (`ps -M`) | 13 | 13 |
| Children (shell, settings child) / zombies | 2 / 0 | 2 / 0 |
| `vmmap` IOSurface regions | 3 | 2 |
| `vmmap` IOAccelerator (graphics) regions | 78 | 77 |

`vmmap -summary` reads the runner without sudo. `ioreg -c IOSurfaceRootUserClient` lists one client per process but not its surfaces, so the region counts stand in for IOSurfaces.

**Not run:** a real log out, restart or shut down (owner checks); a system quit whose child survives SIGKILL, which would show the 4 s reply bound without the watchdog (only the code path and its deadline test exist).
