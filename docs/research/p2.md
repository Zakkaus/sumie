# P2: multi-pane frame budget evidence

Host: desktop with an AMD Ryzen 9 9950X3D (32 threads) and an NVIDIA RTX 4080 SUPER, Linux 7.3.6 with sched_ext, KWin 6.8.3 as a private nested `--virtual` session at scale 1.25 (1600×1000 device pixels). Release build of `p2/u1-budget` (base `main` `a88b5c7`). Copies of the runs are under [`p2/u1/`](p2/u1/).

## U1: frame log and pane harness

**Method.** `scripts/perf/stall.sh ARTIFACTS 60 --panes N --refresh-hz HZ` (see [`REQUIREMENTS.md`](../../REQUIREMENTS.md#presentation-stall-watchdog)). Each pane's shell is a writer printing one changing line every 100 ms; injected Ctrl+Shift+E/O and Ctrl+Alt+Arrow chords build a grid (20 panes: 4 columns of 5 rows). The 60 s interval starts 1 s after the last writer. Presentation events come from the `WAYLAND_DEBUG` trace, and frame stages from `SUMIE_FRAME_LOG`, both on in every run. Frame CPU runs from the start of snapshot refresh to the return of present, on the main thread. Line latency is the time from a writer's write to the return of present for the first frame that snapshotted after it and repainted that pane.

**Results, 2026-11-26 08:20–08:36 (one run each).** The one-minute host load average was 20–40 throughout, because other agents' builds were running.

At 20 panes, the stage p99 values were as follows (60 Hz / 240 Hz):

- snapshots 0.063 / 0.040 ms;
- paint 0.082 / 0.072 ms;
- acquire and submit 0.484 / 0.747 ms;
- present 0.297 / 0.421 ms.

The visible gap includes idle time between lines, so it exceeds 100 ms when few writers run. The stall check therefore measures from each write to the next `presented`.

**What U2 should take from this:**

- **The frame CPU p99 is inside the 240 Hz budget at every pane count.** At 20 panes it was 0.94 ms at 60 Hz and 1.28 ms at 240 Hz, against 4.17 ms. Snapshot and paint stay below 0.1 ms at p99, so drawing 20 panes on the main thread is not close to the limit at this workload.
- **The outliers are in acquire, submit and present, not in our CPU work.** The three slowest frames of the 240 Hz, 20-pane run spent 58, 66 and 91 ms in present. Those of the 60 Hz, 4-pane run spent 26 ms in present and 49 ms in acquire and submit. In an earlier matrix under a load of 30–35, one frame spent 135 ms in acquire and submit, and another 261 ms and then 329 ms in present. The main thread blocks inside wgpu, the driver or the nested compositor while the host is loaded. Partial redraw would not remove these stalls, and a render thread would only move them off the event loop. U2 needs a quiet-host run to tell host contention apart from a real driver stall.
- **At this workload every pane is not dirty in every frame.** Twenty writers at 10 lines/s produce 200 updates/s. At 60 Hz a frame repaints 3.3 panes on average, and at 240 Hz about one. The plan's "dirty every pane every frame" holds only for faster writers. A heavier per-pane workload would test the snapshot and paint scaling.
- **The one stall failure (60 Hz, 4 panes, 119 ms) came with a 49.8 ms acquire-and-submit frame under a load of 20–25.** The 200 ms starvation check passed in all six runs.

**Method finding.** The first two matrices stamped each line only after the write, then only before it. Both showed lines that seemed to wait about 100 ms, one writer period, even with one pane and an idle main thread. Their frames began a few microseconds before the writer's next stamp. The host had preempted the writer for about 100 ms inside its own write. The harness now stamps before and after every write. It counts a frame only if the frame snapshotted after the first stamp, and it measures each wait from the second. It also reports the writes that took over 10 ms (up to 9 of 12,000 here, longest 40 ms).

**Not covered by U1 (U2 runs them):**

- the 4-hour 20-pane gate;
- key latency with 19 busy panes;
- Ghostty on the same workload;
- a quiet-host repeat;
- runs with the frame log or the `WAYLAND_DEBUG` trace off, to compare;
- macOS (`--panes` in `scripts/macos/frames.py` waits for U8 and U9).

The `panes` merge gate runs the same check for 20 s, so a loaded host can fail it through the acquire and present stalls above.
